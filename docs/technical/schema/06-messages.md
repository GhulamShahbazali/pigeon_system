# Section 6: Messages & Chat

> 1-to-1 chat. Text / voice note / image / video. **First-message = request** (TikTok-style): until the recipient accepts, the sender may send only one message. **Block** stops delivery instantly; a blocked sender stays on a **single tick** (never delivered). Ticks ✓ sent · ✓✓ delivered · ✓✓ blue read are **derived**.
> Behaviour locked in `../../product/locked-decisions.md` §6B (M1–M12). Blocks table lives in §1.

---

## Table: `conversations`

One per unique user pair.

| Column | Type | Required | Notes |
|--------|------|----------|-------|
| `id` | UUID | Yes | PK |
| `pair_key` | string | Yes | unique — sorted `min(uid)_max(uid)` so a pair has exactly one conversation |
| `status` | enum | Yes | `pending` \| `accepted` — **request gate** (M3/M4). `pending` until the recipient accepts |
| `initiator_id` | UUID | Yes | FK `users` — who sent the first message (the requester) |
| `last_message_id` | UUID | No | FK `messages` — inbox preview |
| `last_message_at` | timestamp | No | inbox sort |
| `created_at` | timestamp | Yes | |
| `updated_at` | timestamp | Yes | |
| `deleted_at` | timestamp | No | soft delete |

**Indexes:** unique `(pair_key)`; `(last_message_at DESC)` for inbox.

**Rules:**
- Created on the **first message** (no explicit create endpoint). `status='pending'`, `initiator_id = sender`.
- While `pending`: the **initiator may insert only one message** (service check + a partial guard: count of initiator messages in a pending conversation ≤ 1). The recipient accepting flips `status='accepted'` (then both send freely). Delete/Block from the request removes/blocks.

## Table: `conversation_participants`

Per-user state within a conversation (drives read receipts / ticks / mute).

| Column | Type | Required | Notes |
|--------|------|----------|-------|
| `id` | UUID | Yes | PK |
| `conversation_id` | UUID | Yes | FK (cascade) |
| `user_id` | UUID | Yes | FK `users` (cascade) |
| `last_read_message_id` | UUID | No | FK `messages` — everything up to here is **read** (blue ✓✓) for the other party |
| `last_read_at` | timestamp | No | |
| `last_delivered_message_id` | UUID | No | everything up to here is **delivered** (grey ✓✓). Not advanced while blocked → sender stays single ✓ (M8) |
| `is_muted` | boolean | Yes | default false |
| `joined_at` | timestamp | Yes | |

**Indexes:** unique `(conversation_id, user_id)`.

**Tick derivation (no per-message status columns):**
- **✓ sent** — `messages.created_at` exists.
- **✓✓ delivered** — message id ≤ the recipient's `last_delivered_message_id`.
- **✓✓ blue read** — message id ≤ the recipient's `last_read_message_id`.
- **Blocked** — the recipient's device never acks delivery, so `last_delivered_message_id` doesn't advance → the sender's messages stay on single ✓. Clean and automatic.

## Table: `messages`

| Column | Type | Required | Notes |
|--------|------|----------|-------|
| `id` | UUID | Yes | PK |
| `conversation_id` | UUID | Yes | FK (cascade) |
| `sender_id` | UUID | Yes | FK `users` (cascade) |
| `type` | enum | Yes | `text` \| `voice` \| `image` \| `video` |
| `body` | text | No | text content (for `text`; optional caption otherwise) |
| `media_id` | UUID | No | FK `message_media` (for voice/image/video) |
| `created_at` | timestamp | Yes | = **sent** time |
| `deleted_at` | timestamp | No | soft delete (delete-for-both) |

**Indexes:** `(conversation_id, created_at DESC)` partial WHERE `deleted_at IS NULL` — chat scrollback (cursor paginated).

**Rules:**
- **Block check on every send** (both directions, §1 `blocks`) — refused if blocked.
- **Request gate** on the first message of a `pending` conversation (one message until accepted).
- Rate-limited (Redis `rate_limit:messages:{user_id}`).
- On insert: `message.new` to `chat:{id}` + `user:{recipient_id}`; enqueue `dm-push-send` (gated by presence; respects block/request); update `conversations.last_message_*`.
- Voice/image/video reference `message_media`; the file is uploaded first (`POST /v1/uploads` → `media-process` worker) and the `upload_id` is passed here.

## Application-layer patterns
- **Inbox** = conversations where the user is a participant and `status='accepted'`, sorted by `last_message_at`. **Requests** = conversations where the user is the *recipient* and `status='pending'`.
- **Typing / recording** are Redis TTL keys (`typing:*`, `recording:*`), socket events only — never stored.
- **Read receipt** = client advances `last_read_message_id` → `chat.read` emit → sender's ticks turn blue.
